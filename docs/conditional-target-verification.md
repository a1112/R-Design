When a selected node exists only inside a route or an opened panel, candidate verification must return to that node before reading the changed properties. Previously the final keyboard check navigated to `/`, so a settings heading could pass every scenario and then fail its property readback because the heading was absent.

Preparing a change now stores the selected same-origin route and viewport in the private change metadata. If that target was captured through a registered scenario, it also stores the scenario entry route, declared steps and readiness selector. Verification restores that context after the general checks, then requires one visible instance with the original exact source binding. It reads the actual changed properties and captures that page as the candidate frame.

The scenario runner also restores its caller's registered context. On a source reload, the live runtime replays that context so registered panels opened through steps survive apply/revert. An intervening live navigation remains independent from candidate verification; an unexpected navigation during restoration fails verification. Direct user click/key input invalidates the remembered scenario rather than silently replaying a stale panel state.

This does not serialize arbitrary React state, Redux state, browser storage, cookies or form values. State required for a conditional target must be reproducible by its route and registered steps. New runtime/store instances can verify an existing prepared change using its persisted metadata. Source acceptance still commits before runtime synchronization, preserving the existing failure semantics. Controlled property revert restores the property; the existing AST transformer may normalize source formatting.

`tests/protocol/conditional-target-context.test.ts` uses only disposable synthetic source. It covers a non-root settings route that requires two stateful clicks, all-scene restoration, original-target property readback, repeated verification, an idempotent repeated apply request, apply/revert reload, runtime/store restart, intervening live navigation, interrupted target restoration and a clean retry. The separate actual R-msg evidence is kept privately outside this repository.
